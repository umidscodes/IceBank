# Ice Bank — Build Spec

Nov 4, 2026 · @Maierdan Wumitijiang

## Overview

Ice Bank is a fictional Canadian bank built only as a test target, so three students can go from QA fundamentals to job-ready in REST Assured, Selenium, SQL/JDBC and JMeter. Students already know Java and are nearly done with Selenium; the next three weeks focus on API and database testing.

| # | Deliverable | Used by | Runs on |
| --- | --- | --- | --- |
| 1 | **Ice Bank** (clean build) | Students | Each student's Windows PC, `npm run dev` |
| 2 | **Ice Bank QA** (buggy build) | Students; bugs controlled by the instructor | Vercel + Supabase, deployed from a private repo |
| 3 | **Tutorial site** | Students | Standalone static HTML; progress saved in the browser |
| 4 | **Instructor pack** | Instructor only | Private repo |

**Guiding principles**

- **Realistic, not a toy.** Behaves like a big-five Canadian online bank: real validation, real business rules, real error messages.
- **Testable by design.** Documented API (Swagger), stable `data-testid` locators, deterministic seed data, one-call reset, a controllable app clock.
- **One codebase, two builds.** Clean and buggy are the same code; bugs are server-side overrides that only exist in the private repo.
- **One-command setup.** Windows, Node.js and Git only. No Docker, no manual database install.
- **Black box for students.** They never need the source, and the student repo never contains bug code.

**Out of scope for v1:** mobile app, French language, CI pipelines, real emails or payments (an in-app inbox called **Ice Mail** stands in for email).

## Architecture & tech stack

One Next.js app serves the bank UI, the REST API and Swagger from a single process, backed by PostgreSQL. It builds in two flavours from one private repo: `clean` for students and `qa` for the hosted bug-hunt environment.

&#91;embedded content: Ice Bank architecture: two repos, two environments, one test framework\]

Students point one framework at both environments by switching `env`; only the private repo ever contains bug code.

| Layer | Choice | Notes |
| --- | --- | --- |
| App | Next.js (latest stable, App Router) + TypeScript | UI pages and API route handlers in one process on port 3000 |
| API | Route handlers under `/api/v1` | OpenAPI 3 spec at `/api/v1/openapi.json`, Swagger UI at `/swagger` |
| Database | PostgreSQL 16 | Local: `embedded-postgres` npm package on port 5433, started by `npm run dev`. Hosted: Supabase |
| Data access | Prisma for the app; raw SQL migrations for triggers, views and functions | Migrations and seed run automatically on first `npm run dev` |
| Validation | Zod | One schema per request body; drives both API errors and the OpenAPI spec |
| Auth | JWT access token (15 min) + refresh token (7 days); UI stores them in httpOnly cookies | Passwords hashed with bcrypt |
| UI | Tailwind CSS, Inter font | Clean big-five bank look (see UI section) |
| App self-tests | Vitest smoke tests | Guard the clean build so its behaviour is the true expected result |
| Runtime | Node.js LTS (24.x) on Windows 11 | Git is the only other prerequisite |

**Environments**

| Env | Build | Database | URL | Bugs |
| --- | --- | --- | --- | --- |
| `local` | clean | Embedded Postgres, `localhost:5433` | `http://localhost:3000` | None; the bug module is not in the code |
| `qa` | qa | Supabase Postgres | Vercel project URL, e.g. `icebank-qa.vercel.app` | Packs set by the instructor |

**Repos**

- **`ice-bank-private`** (instructor): full code, the `src/bugs` module, `instructor/` folder. Vercel deploys QA from here.
- **`ice-bank`** (students): generated by `npm run export:student`, which copies the repo without `src/bugs`, `instructor/` and QA-only migrations, then pushes to the student repo.

**Bug hook design (so the student repo leaks nothing).** Every service function is wrapped the same way, `hookable('transfers.create', impl)`, whether or not a bug targets it. In the clean build `hookable` returns `impl` unchanged. In the QA build it checks the active packs for the sandbox and swaps in an override from `src/bugs`. Because every function is wrapped uniformly, call sites reveal nothing about where bugs live.

## Banking features

Every feature has exact business rules, because the rules are the test oracle: students must be able to say what the correct result is before they test. Numbers below are the clean build's behaviour.

**Customer features**

| Area | Feature | Business rules |
| --- | --- | --- |
| Onboarding | Multi-step registration (personal info, address, security, review) | Age 18+; Canadian postal code `A1A 1A1`; province from the 13 provinces/territories; phone `(###) ###-####`; fake SIN validated with the Luhn check; email unique per sandbox; new customer gets a chequing account |
| Login & security | Email + password, then 6-digit OTP sent to Ice Mail | Password 8 to 64 chars with upper, lower, digit and special; 5 failed logins lock the user for 15 min; OTP expires after 5 min, 3 attempts max; idle session ends at 10 min with a warning modal at 9 min |
| Login & security | Forgot / reset password | Reset link to Ice Mail, valid 30 min, single use; new password cannot equal the last 3 |
| Accounts | Chequing, Savings, Credit card, Personal loan | Account number = institution `999` (fictional), 5-digit transit, 7-digit account. Savings: 2.25% annual interest, accrued daily, paid monthly. Credit card: limit $5,000, 20.99% APR, minimum payment = greater of $10 or 3% of balance |
| Accounts | Open a new savings account | Max 3 savings accounts per customer; optional nickname 1 to 30 chars |
| Transactions | List, filter, sort, paginate, search | Filters: date range (inclusive both ends), type, amount min/max, description text; page size 1 to 100, default 20; newest first |
| Transactions | CSV export and monthly PDF statement | CSV columns fixed and documented; statement shows opening and closing balance |
| Transfers | Between own accounts | Instant; $0.01 to $999,999.99; max 2 decimals; cannot exceed available balance; source and target must differ; frozen accounts blocked |
| Interac e-Transfer | Send to email | Per transfer $0.01 to $3,000; daily $3,000; rolling 30-day $10,000 (pending transfers count toward limits); security question plus answer 3 to 25 chars, case-insensitive, not in the message; recipient with autodeposit gets it instantly, otherwise pending until accepted; sender can cancel while pending (full refund); expires after 30 days |
| Interac e-Transfer | Contacts and autodeposit | Up to 50 contacts; autodeposit email must belong to the customer and be confirmed by OTP |
| Bill payments | Billers directory, saved payees, pay now or schedule | Fictional billers (Niagara Power Co, IceTel Mobile, Maple Gas, City of Iceport Water); each biller has an account-number format; payments post next business day; weekends and Canadian statutory holidays skipped |
| Bill payments | Recurring payments | Weekly, biweekly, monthly; a monthly payment on the 29th to 31st falls on the last day of shorter months; cancel any future occurrence |
| Cheque deposit | Upload front and back image + amount | JPG or PNG, max 5 MB each; daily limit $5,000; first $100 available immediately, rest pending until an admin approves |
| Cards | Debit and credit cards | Lock/unlock instantly; report lost cancels the card and issues a new Luhn-valid number; daily debit POS limit adjustable $500 to $5,000 in $100 steps; numbers always masked to last 4 |
| Loans | Personal loan application | $1,000 to $50,000; term 12 to 60 months; deterministic decision: debt-to-income under 35% approved, 35 to 45% manual review, over 45% declined; approved loan shows a full amortization schedule |
| Disputes | Dispute a posted transaction | Within 60 days of posting; reason from a fixed list; one open dispute per transaction |
| Notifications | In-app notifications | Created on every money movement, login from a new session and security change |
| Ice Mail | Simulated email inbox | Holds OTPs, reset links and e-transfer notices; opens in a new tab |
| Profile | Edit address, phone, email, password | Email change needs an OTP to the new address |

**Admin (teller) portal**, role `ADMIN`: search customers; view any customer's accounts; freeze and unfreeze accounts; unlock locked users; approve or reject cheque deposits; decide loans in manual review; view the audit log. Customers must never reach admin pages or endpoints.

**Test-support features** (present in both builds, documented for students)

- **Reset:** restores the sandbox to its exact seed state, same IDs.
- **App clock:** each sandbox has a virtual date that can be moved forward, so students can test scheduled payments, interest, expiry and holidays without waiting.
- **Ice Mail API:** lets automated tests read OTPs and links, the way real teams use a test mailbox.

## REST API

The API is the main teaching surface, so it follows strict, documented conventions and every endpoint appears in Swagger with example requests, responses and error cases.

**Conventions**

| Topic | Rule |
| --- | --- |
| Base path | `/api/v1`, JSON only, camelCase fields |
| Money | Decimal strings with exactly 2 places, e.g. `"1250.00"`; stored as `NUMERIC(14,2)` (teaches `BigDecimal`, not `double`) |
| Dates | ISO 8601 with offset, e.g. `2026-11-04T21:15:00-05:00`; dates without time as `2026-11-04` |
| Auth | `POST /auth/login` returns `{mfaRequired, mfaToken}`; `POST /auth/mfa/verify` returns `{accessToken, refreshToken, expiresIn}`; then `Authorization: Bearer <token>` |
| Errors | RFC 7807 `application/problem+json`: `type`, `title`, `status`, `detail`, `instance`, plus `errors[{field, message}]` for validation |
| Status codes | 200 OK; 201 Created + `Location` header; 204 No Content; 400 malformed or invalid input; 401 no or bad token; 403 wrong role; 404 not found, also for another customer's resource; 409 duplicate or state conflict; 422 business rule broken (e.g. insufficient funds, limit exceeded); 429 rate limited with `Retry-After` |
| Pagination | `?page=0&size=20&sort=createdAt,desc` returns `{content, page, size, totalElements, totalPages}` |
| Idempotency | `Idempotency-Key` header required on money-moving POSTs; same key + same body replays the first response; same key + different body returns 409 |
| Tracing | Every response carries `X-Request-Id` |
| Rate limits | Login 10 per minute per IP; all other endpoints 120 per minute per user; `PERF_MODE=true` disables limits locally for JMeter |

**Endpoint catalogue** (all under `/api/v1`)

| Group | Endpoints |
| --- | --- |
| Auth | `POST /auth/register`, `POST /auth/login`, `POST /auth/mfa/verify`, `POST /auth/refresh`, `POST /auth/logout`, `POST /auth/password/forgot`, `POST /auth/password/reset` |
| Profile | `GET /me`, `PATCH /me`, `PUT /me/password`, `POST /me/email-change`, `POST /me/email-change/confirm` |
| Accounts | `GET /accounts`, `POST /accounts`, `GET /accounts/{id}`, `GET /accounts/{id}/transactions`, `GET /accounts/{id}/transactions.csv`, `GET /accounts/{id}/statements`, `GET /accounts/{id}/statements/{yyyy-mm}.pdf` |
| Transfers | `POST /transfers`, `GET /transfers`, `GET /transfers/{id}` |
| Interac e-Transfer | `POST /etransfers`, `GET /etransfers?direction=sent\|received`, `GET /etransfers/{id}`, `POST /etransfers/{id}/cancel`, `POST /etransfers/{id}/accept`, `GET /etransfers/autodeposit`, `PUT /etransfers/autodeposit`, `GET\|POST /etransfer-contacts`, `PUT\|DELETE /etransfer-contacts/{id}` |
| Bill payments | `GET /billers?q=`, `GET\|POST /payees`, `PUT\|DELETE /payees/{id}`, `POST /bill-payments`, `GET /bill-payments`, `DELETE /bill-payments/{id}` (cancel scheduled) |
| Deposits | `POST /deposits/cheque` (multipart), `GET /deposits`, `GET /deposits/{id}` |
| Cards | `GET /cards`, `POST /cards/{id}/lock`, `POST /cards/{id}/unlock`, `POST /cards/{id}/report-lost`, `PATCH /cards/{id}/limits` |
| Loans | `POST /loans/applications`, `GET /loans/applications/{id}`, `GET /loans`, `GET /loans/{id}/schedule` |
| Disputes | `POST /disputes`, `GET /disputes`, `GET /disputes/{id}` |
| Notifications | `GET /notifications`, `POST /notifications/{id}/read` |
| Ice Mail | `GET /inbox`, `GET /inbox/{id}` |
| Admin | `GET /admin/customers?q=`, `GET /admin/customers/{id}`, `POST /admin/accounts/{id}/freeze`, `POST /admin/accounts/{id}/unfreeze`, `POST /admin/users/{id}/unlock`, `GET /admin/deposits?status=`, `POST /admin/deposits/{id}/approve`, `POST /admin/deposits/{id}/reject`, `GET /admin/loans?status=`, `POST /admin/loans/{id}/decision`, `GET /admin/audit-log` |
| Test support | `GET /test/health`, `POST /test/reset`, `GET /test/clock`, `POST /test/clock` (set or advance the sandbox date) |
| Training (QA build only, instructor role) | `GET /training/bugs`, `PUT /training/bugs`, `POST /training/mystery`, `GET /training/reveal` |

Test-support calls need an `X-Sandbox-Key` header so a student can only reset or move the clock of their own sandbox.

## Database

The schema is built so database testing has real substance: constraints, transactions, a trigger-fed audit log, views and a stored function, all of which students verify over JDBC. Every business table carries `sandbox_id` (always `1` locally; one per student on QA).

**Tables**

| Table | Holds | Key constraints |
| --- | --- | --- |
| `sandboxes` | One row per student data partition | `key_hash`, `clock_offset_days` |
| `users` | Login identity | Email unique per sandbox; `role` in (`CUSTOMER`, `ADMIN`, `INSTRUCTOR`); `status` in (`ACTIVE`, `LOCKED`, `DISABLED`); `failed_login_count`, `locked_until` |
| `customers` | Personal details | FK to `users`; `province` CHECK against the 13 codes; `postal_code` CHECK regex; `date_of_birth` CHECK age 18+ at creation; SIN stored hashed + last 3 digits |
| `accounts` | Chequing, savings, credit, loan | `account_number` unique; `type` CHECK; `balance` and `available_balance` `NUMERIC(14,2)`; CHECK `balance >= 0` for chequing and savings; CHECK `balance >= -credit_limit` for credit; `status` in (`OPEN`, `FROZEN`, `CLOSED`) |
| `transactions` | Every money movement, one row per account leg | `amount > 0`; `direction` in (`DEBIT`, `CREDIT`); `balance_after`; `status` in (`PENDING`, `POSTED`, `REVERSED`); `reference_id` links both legs |
| `transfers`, `etransfers`, `etransfer_contacts` | Transfer records and contacts | e-transfer `status` in (`PENDING`, `DEPOSITED`, `CANCELLED`, `EXPIRED`); `security_answer_hash` |
| `billers`, `payees`, `bill_payments` | Biller directory, saved payees, scheduled and recurring payments | `recurrence` in (`NONE`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`); FK `payee_id` with `ON DELETE RESTRICT` |
| `cheque_deposits` | Uploaded images (bytea) and hold status | Image max 5 MB; `status` in (`PENDING`, `APPROVED`, `REJECTED`) |
| `cards` | Debit and credit cards | Card number stored encrypted + `last4`; `status` in (`ACTIVE`, `LOCKED`, `CANCELLED`) |
| `loan_applications`, `loans`, `loan_schedule` | Applications, decisions, amortization rows | Schedule rows sum to principal + interest |
| `disputes` | Transaction disputes | Partial unique index: one `OPEN` dispute per transaction |
| `notifications`, `inbox_messages` | In-app notifications and Ice Mail | `read_at` nullable |
| `otp_codes`, `refresh_tokens`, `idempotency_keys` | Security and idempotency | OTP stored hashed with `expires_at` and `attempts`; idempotency key unique per user |
| `audit_log` | Who changed what | `actor_user_id`, `action`, `entity_type`, `entity_id`, `old_value` and `new_value` as JSONB, `created_at` |
| `training_state` | Active bug packs per sandbox | **QA build only**; never in the student repo |

**Database objects students test**

- **Function `post_transfer(from_account, to_account, amount, reference)`** moves money atomically: two transaction rows, two balance updates, one audit row, or nothing at all. Callable over JDBC with `CallableStatement`.
- **Trigger `trg_transactions_audit`** writes an `audit_log` row on every insert or status change in `transactions`.
- **Trigger `trg_transactions_immutable`** blocks UPDATE of amount or account and any DELETE on `POSTED` transactions.
- **View `v_account_summary`**: account, balance, pending count, last transaction date.
- **View `v_daily_etransfer_totals`**: per customer per day, used for limit checks.

**Seed data** is deterministic (fixed IDs and fixed random seed), so tests can hard-code IDs and expect identical data after every reset. Each sandbox gets about 50 customers with two years of history, plus documented personas:

## UI and Selenium testability

The UI should look like a real big-five Canadian online bank, clean and calm, while giving students every common Selenium challenge in places where it naturally belongs.

**Look and feel**

- Brand: **Ice Bank**, an ice-cap logo mark; deep navy `#0B2545`, glacier blue `#4FA3D9`, frost white `#F5F9FC`, success green and alert red for states.
- Inter font, generous spacing, card-based dashboard, desktop-first but responsive down to 1024 px.
- WCAG 2.1 AA contrast, visible focus states, labelled form fields.
- Fictional brand only: no real bank names, logos or colours copied.

**Pages**

| Area | Pages |
| --- | --- |
| Public | Landing, Login, OTP verification, Forgot password, Reset password, Registration wizard (4 steps) |
| Banking | Dashboard, Account details with transactions table, Transfer, Interac e-Transfer (send, received, contacts, autodeposit), Bill payments (pay, payees, scheduled), Deposit cheque, Cards, Loans (apply, status, schedule), Statements, Disputes, Notifications, Profile and security |

## Bug packs and Training Console

The QA build ships about 34 planted bugs in 7 packs, switched on per sandbox by the instructor; students hunt them on the hosted site and the instructor reveals them afterwards.

**Mechanism**

- Each bug is an override in `src/bugs/<pack>/<bug-id>.ts` registered against a `hookable` name (see Architecture). Overrides change behaviour only; they never change the API shape or the UI layout, so students' automated tests keep running.
- Active packs are stored per sandbox in `training_state`. Changes apply on the next request, no redeploy.
- **Modes:** *Off* (clean behaviour), *Packs* (instructor picks packs per sandbox), *Mystery* (the app enables a random set of bugs and records which).
- **Training Console** at `/training`, `INSTRUCTOR` role only: pick sandbox, toggle packs, start Mystery, reveal the active list, reset a sandbox. Same actions via `/api/v1/training/*`.
- Pack names shown anywhere students could see them are neutral ("Pack 3"); descriptions live only in the instructor pack.
- Every bug must be catchable by at least one API, DB or UI test, and the catalogue names which layer catches it.

**Catalogue outline** (full catalogue with reproduction steps, expected vs actual and catching layer goes in the instructor pack)

| Pack | Area | Planted bugs | Caught by |
| --- | --- | --- | --- |
| 1 | Auth and session | Lockout after the 6th failed login instead of the 5th; expired OTP still accepted; refresh token still works after logout; password without a special character accepted; "Stay signed in" in the timeout modal does not extend the session | API, UI |
| 2 | Transfers | Transfer of exactly the available balance rejected; transfer to the same account allowed; 3-decimal amount silently rounded instead of rejected; idempotency key ignored, so a retry creates a duplicate transfer; transfer from a frozen account allowed | API, DB |
| 3 | Interac e-Transfer | Pending transfers not counted toward the daily limit; security answer treated as case-sensitive; cancelled transfer not refunded (no reversal row); invalid recipient email accepted; expired transfer still acceptable | API, DB |
| 4 | Bill payments and scheduling | Saturday payment posts Saturday instead of Monday; Canada Day not treated as a holiday; monthly payment on the 31st skips 30-day months; payee account-number format not validated | API, DB, clock |
| 5 | Data integrity | `balance_after` wrong when two transactions land in the same second; no audit row for e-transfer cancellation; balance updated but transaction row missing after a failure (not atomic); deleted payee leaves scheduled payments orphaned; interest posted to the wrong savings account | DB |
| 6 | API contract and security | Another customer's account readable by ID (IDOR); malformed JSON returns 500 instead of 400; `totalElements` off by one; timestamps returned without offset; `POST /payees` returns 200 without `Location`; customer token can call an admin endpoint | API |
| 7 | UI | Dashboard total adds the credit card balance instead of subtracting it; amount column sorts as text; date filter excludes the end date; success toast shown when the API returned an error; masked card number shows first 4 digits instead of last 4 | UI |

## Hosted QA environment

Ice Bank QA runs on the instructor's existing free Vercel (Hobby) and Supabase accounts, deployed from the private repo, with one data sandbox per student.

**Setup**

1. Supabase: create one project. Run `npm run db:migrate:qa` then `npm run db:seed:qa -- --sandboxes=3` (sandbox 0 for the instructor, 1 to 3 for students).
2. Create the read-only `qa_reader` role (script included) and share the session-pooler connection string with students.
3. Vercel: import `ice-bank-private`, set environment variables: `BUILD_FLAVOR=qa`, `DATABASE_URL` (Supabase pooler), `JWT_SECRET`, `JWT_REFRESH_SECRET`, `CARD_ENCRYPTION_KEY`, `INSTRUCTOR_EMAIL`, `INSTRUCTOR_PASSWORD`.
4. Give each student: the QA URL, their sandbox key, their sandbox's persona logins and the `qa_reader` connection string.

**Free-tier constraints and how the design handles them**

| Constraint | Design response |
| --- | --- |
| Supabase free projects pause after 7 days without activity | Daily Vercel cron calls `GET /api/v1/test/health`, which runs a small query |
| Vercel Hobby cron runs at most once a day | No frequent background jobs. Due work (scheduled payments, interest, e-transfer expiry, pending to posted) is processed lazily at the start of any request for that sandbox, based on the sandbox clock |
| Supabase free database is 500 MB | Seed data stays well under 100 MB; cheque images capped at 5 MB and pruned on reset |
| Vercel Hobby is personal, non-commercial use | Fits: free teaching for three friends |
| Serverless limits | JMeter is never pointed at QA; load testing is local only |

**Sandbox rules**

- Logging in as a persona puts you in that persona's sandbox; nobody can see another sandbox's data through the app.
- Reset and clock calls need the sandbox key, so a student can only affect their own sandbox.
- `qa_reader` can read all sandboxes; students filter by `sandbox_id`, which is itself a realistic multi-tenant SQL lesson.

## Tutorial site

The tutorial site is a standalone static site (plain HTML, CSS and JavaScript, no build step) in `tutorials/` of the student repo, covering six foundation topics with tick-box progress saved in each student's browser.

**Site behaviour**

- Open with `npm run tutorials` (serves on `http://localhost:4000`); can also be deployed to Vercel as a static site.
- Sidebar with the six tutorials and their lessons; each lesson has explanation, Ice Bank examples with copy buttons, and exercises with tick boxes.
- Progress bar per tutorial and an overall percentage at the top.
- A notes box per lesson.
- Progress and notes stored in `localStorage` under `icebank-tutorials-v1`, every read and write wrapped in `try/catch`; the site works even if storage is unavailable.
- **Export / Import progress** buttons save and load a JSON file, so progress survives a cache clear or a new laptop. A **Reset progress** button asks for confirmation.
- Same Ice Bank visual style as the app. Links like "open Swagger now" point to `http://localhost:3000`.
- No answers on the site; answer keys live in the instructor pack.

**Content**

| # | Tutorial | Lessons |
| --- | --- | --- |
| 1 | SQL fundamentals | DBeaver setup and connecting to Ice Bank; SELECT, WHERE, ORDER BY; aggregates and GROUP BY; JOINs; subqueries and CTEs; INSERT, UPDATE, DELETE and transactions; constraints; views, triggers and functions; the QA query toolkit |
| 2 | HTTP and APIs | Client and server, URL anatomy; methods and idempotency; status codes; headers and content types; JSON; cookies, JWT and refresh tokens; REST conventions and pagination; reading Ice Bank's Swagger contract; Postman collections, environments and chaining |
| 3 | Browser DevTools | Elements panel and testing CSS/XPath with `$$` and `$x`; Network tab filtering and inspecting requests; Copy as cURL; Console errors; Application tab (cookies, storage, decoding a JWT); network throttling; tracing a UI bug to its API call |
| 4 | Git and GitHub | Core concepts; clone, add, commit; branches; push and pull; pull requests and review; merge conflicts; `.gitignore` for `target/` and secrets; commit messages; a team workflow |
| 5 | Manual QA fundamentals | SDLC and STLC; test plan vs test strategy; anatomy of a test case; equivalence partitioning and boundary values (e-Transfer limits); decision tables (loan decisions); state transitions (account lockout); exploratory testing with charters; bug report anatomy, severity vs priority; Jira workflow; smoke, sanity and regression; QA in Agile ceremonies |
| 6 | Framework hygiene | Project structure; config per environment (`local`, `qa`) with `-Denv`; keeping secrets out of Git; test data strategy (API setup, DB checks, reset); logging with SLF4J and REST Assured filters; Allure steps, attachments and history; flaky tests and retries; naming and tagging; writing a framework README |

Every lesson ends with 2 to 5 exercises run against Ice Bank, local or QA.

## Repo layout, commands and build order

Build in the 12 milestones below, each one runnable before the next starts; the build is done when every acceptance check passes.

**Repo layout** (`ice-bank-private`)

```
src/app/             UI pages (App Router)
src/app/api/v1/      REST route handlers
src/server/services/ business logic, every function wrapped in hookable()
src/server/db/       Prisma client, SQL helpers
src/bugs/            bug overrides by pack            (private only)
src/lib/             shared utils: money, dates, business days, validation
db/migrations/       Prisma + raw SQL (triggers, views, function, roles)
db/seed/             deterministic seed and personas
openapi/             OpenAPI generation from Zod schemas
tutorials/           static tutorial site
instructor/          instructor pack                  (private only)
scripts/             dev.ts (embedded Postgres), export-student.ts, qa setup
README.md            setup, credentials, personas, locator list
```

**Commands**

| Command | Does |
| --- | --- |
| `npm install` | Installs everything, including the embedded Postgres binaries |
| `npm run dev` | Starts Postgres on 5433, migrates, seeds if empty, starts the app on 3000 |
| `npm run reset` | Restores seed data (same as `POST /test/reset`) |
| `npm run tutorials` | Serves the tutorial site on 4000 |
| `npm test` | App smoke tests |
| `npm run export:student` | Builds the clean student repo and pushes it (private repo only) |
| `npm run db:migrate:qa`, `npm run db:seed:qa` | Prepare Supabase (private repo only) |

README includes a fallback: `docker compose up` for anyone whose embedded Postgres fails on Windows.

**Build order**

1. Foundation: Next.js skeleton, `dev.ts` with embedded Postgres, migrations, seed, auth with OTP and Ice Mail.
2. Core banking: accounts, transactions, internal transfers, dashboard and app shell.
3. Payments: Interac e-Transfer, bill payments, business-day and holiday logic, app clock, lazy due-work processing.
4. Cheque deposits, cards, loans with amortization, disputes, notifications, profile.
5. Admin portal.
6. API polish: RFC 7807 errors, idempotency, rate limits, `X-Request-Id`, OpenAPI and Swagger complete.
7. Database objects: `post_transfer`, triggers, views, `qa_reader` and `qa_writer` roles.
8. Selenium challenges and Classic view.
9. Bug framework, 7 packs, Training Console, `export:student` script.
10. QA deployment on Vercel and Supabase with 4 sandboxes and keep-alive cron.
11. Tutorial site and all six tutorials.
12. Instructor pack.
